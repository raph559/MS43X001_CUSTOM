# Live-tuning RAM overlay — design for the car's MS43X001

Status: **design, not built.** Nothing has been flashed, nothing written to the car, no code
patched yet. All addresses below were read out of the car's own file
`bins/CAR_current_43X001_SP95_STAGE1.bin` (SHA-256 `8cfe3124…c0717`).

Labels follow REPORT.md: **[obs]** seen in the bytes, **[ver]** recomputed by a tool here,
**[inf]** inference.

---

## 1. What the car runs, and why it matters

| Fact | Value | Why it matters |
|---|---|---|
| Program code | byte-identical to the MS43X001 release, except 26 ASCII bytes at 0x4FFE6–0x4FFFF | The car is MS43X001, not stock 430069. Anything derived from stock is only valid where noted. |
| Lookup library | file 0x50002–0x510EB, **byte-identical to stock 430069** [ver] | A hook in the library behaves identically on the car. |
| Calibration tables | **856**, not 858 [ver] | The stock catalogue (`calmaps.csv`) is *not* the car's table set. |
| Named tables | **839 of 856** [ver] | The MS4X `MS43X001` XDF v1.0.0 names and scales the car's own tables. |

Free flash for new code: file **0x4B545–0x4FFFF** (≈19 KiB, CPU 0C:B545–0C:FFFF). MS43X001
already uses 0x4A8CC–0x4B544; the rest of that sector is still erased in the car file [obs].

## 2. The live-edit targets

Names come from `defs/Siemens_MS43_MS43X001_512K_v1.0.0.xdf` (MS4X Dev Team, autogenerated,
BASEOFFSET 0x70000) and are confirmed against the car's bytes. "Used on this car" means the
feature is enabled in the car's calibration.

| Address | Name | Shape | Bytes | Used on this car |
|---|---|---|---|---|
| 0x7EE20 … 0x7FC20 | `ip_map_ve_1..8__map__n` | 16×16 u16 | 512 each, 4096 total | **Yes** — these *are* the fuel map on MS43X001 (load = VE × MAP × rpm) |
| 0x771D5 | `ip_iga_ron91_pl__n__maf` | 20×16 u8 | 320 | **Yes** — ignition, RON91 base |
| 0x77315 | `ip_iga_ron98_pl__n__maf` | 20×16 u8 | 320 | **Yes** — ignition, RON98 base |
| 0x77494 | `ip_iga_e85_pl__n__maf` | 20×16 u8 | 320 | Read but blended out (flex fuel off, factor 8484 = 0) |
| 0x7D69C | `ip_af_target_ron98__maf__n` | 12×16 u8 | 192 | **Yes** — target λ/AFR at full load, gasoline |
| 0x7D75C | `ip_af_target_e85__maf__n` | 12×16 u8 | 192 | Blended out (flex fuel off) |
| 0x7D974 | `ip_ti_fac_map__map` | 16×1 u8 | 16 | Yes — injection correction vs MAP (new in MS43X001) |
| 0x7D984 | `ip_ti_fac_ti__ti` | 16×1 u8 | 16 | Yes — injection correction vs pulse width |
| 0x770A5 | `ip_iga_optm_ron98__n__maf` | 16×12 u8 | 192 | MBT reference, limits torque intervention |
| 0x76FE5 | `ip_iga_optm_e85__n__maf` | 16×12 u8 | 192 | Blended out |

**There is no base injection map on MS43X001** [obs, MS43X001_DIFF.md §2]. Fuel is
`load × 477 / K` with K = injector flow (0x70E14 = 225 on the car) × AFR (0x70E11) × density
(0x70E12), times the enrichment factors. So "live tuning of injection" on this car means the
**VE maps** and the **AFR target maps**, not a pulse-width table.

### Why the ignition pair is the practical target

The ignition path [obs, disassembly at 0x2C628–0x2C692]:

```
R4 = ron91(0x771D5) + (ron98(0x77315) − ron91)·octane_factor      ; 0x2C650…0x2C678
R4 = blend(R4, e85(0x77494), flex_factor 8484)                    ; 0x2C684…0x2C692
```

With flex fuel off (8484 = 0) the effective map is built from **ron91 and ron98 only**, so
shadowing those two (640 B) covers all ignition tuning. The E85 twin is still *read* by the
code, so it must remain readable — it can stay in flash.

## 3. The hook: redirect the call, not the library

Both hot paths read their table with an **explicit address in a register, immediately before
the call** [obs]. That means the call target itself can be changed — same instruction size,
no code to relocate, no library-wide slowdown.

### VE maps — file 0x3B9DA–0x3BA48

```
03B9DA  MOVBZ R4, E31Dh          ; valve-overlap index 1..8
03B9DE  SUBB RL4, #1h
03B9E0  CMPB RL4, #7h            ; clamp to 0..7
03B9E6  MOVBZ R6, RL4
03B9E8  SHL  R6, #1
03B9EA  ADD  R6, #4CE4h          ; -> 0x0C:CCE4 (DPP1 page), the 8-entry table
03B9F2  MOV  R12, [R6]           ; page-0x1F offset of VE map[index]
03B9F4  MOV  R13, #001Fh
03B9F8  CALLS 0Dh, 0168h         ; read + bilinear interpolate
...
03BA18  MOV  R12, [R6+#0002h]    ; VE map[index+1]
03BA20  CALLS 0Dh, 0168h
03BA42  MOV  R12, [R6]           ; index 7 path
03BA48  CALLS 0Dh, 0168h
```

The 8-entry table at **CPU 0x0C:CCE4 (file 0x6CCE4)** holds the page-0x1F offsets
`2E20, 3020, 3220, 3420, 3620, 3820, 3A20, 3C20` [ver] — i.e. the 8 VE maps at file
0x7EE20 + 0x200·i. The axis searches at 0x3B9C6/0x3B9D6 use `ldpm_ve_map` (count 0x77E60,
16×u16 kPa) and `ldpm_ve_n` (count 0x77E82, 16×u16 rpm).

**Hook:** change the three `CALLS 0Dh, 0168h` to `CALLS 0Dh, <stub>`. The stub sees
R12 = the flash offset and R13 = 0x1F, and substitutes the RAM address if that table is
shadowed. Nothing else about the path changes.

### Ignition maps — file 0x2C648–0x2C684

```
02C648  MOV R12, #3315h ; MOV R13, #001Dh ; CALLS 0Dh, 029Ah   ; ron98
02C656  MOV R12, #31D5h ; MOV R13, #001Dh ; CALLS 0Dh, 029Ah   ; ron91
02C67C  MOV R12, #3494h ; MOV R13, #001Dh ; CALLS 0Dh, 029Ah   ; e85
```

**Hook:** the same trick — redirect the three `CALLS 0Dh, 029Ah` to the stub. R12/R13 carry
the flash address (0x3315 / 0x31D5 / 0x3494 in page 0x1D) at the call.

### AFR target maps

Read at 0x3D40A (0x7D69C) and 0x3D41A (0x7D75C) with the same pattern → same hook.

## 4. The stub and the directory

One generic stub, shared by every redirected call:

```
stub:
    if (overlay_enabled == 0) goto real_reader        ; default-off, one byte test
    for each directory entry (flash_off, flash_page, ram_off, ram_page, size):
        if (R12 == flash_off and R13 == flash_page and active):
            R12 = ram_off ; R13 = ram_page
    real_reader:                                       ; JMPA to the original helper
        JMPA 0Dh, 0168h / 029Ah / ...
```

The directory lives in RAM and is written by the host over K-line. Suggested layout, 8 entries:

| Offset | Size | Meaning |
|---|---|---|
| 0x00 | 1 | overlay enable (0 = stock, 1 = live) |
| 0x01 | 1 | entry count |
| 0x02 | 6·8 | per entry: u16 flash offset, u8 flash page, u16 RAM offset, u8 RAM page, u8 flags |

48 bytes + 1 byte of shadow data bookkeeping. The stub must not disturb registers the readers
need; the emulator is the only acceptable way to settle that.

**Default-off and reset-to-stock:** the enable byte is cleared at every key-on (the same place
the RAM-size class byte 8494 is written, 0C:5C80) and on every DS2 session start. A
watchdog-free failure therefore leaves the ECU on stock calibration.

## 5. RAM budget — the car has 8 KiB, confirmed

The owner ran `tools/ds2_read_mem.ps1 -RamCheck` (read-only, DS2 command 06) on the car on
2026-10-19 and reported an **8 KiB** external SRAM. That matches the MS4X wiki's component list
(ZMD U62H64SA, "Automotive Fast 8K x 8 SRAM") [ext].

Consequences:

- The free block is **736 B at 9D00–9FDF** and nothing more: A906–BFFF does not exist on this
  board, so the "16 KiB" branch of the design is dead.
- The runtime check of the RAM-size class byte **8494** is still worth keeping in the firmware —
  it costs one byte read and protects anyone who flashes this image to a 16 KiB board — but the
  shadow area must default to the 8 KiB layout.

### What 736 B buys

| Shadow set | Bytes | Fits? |
|---|---|---|
| `ip_iga_ron91_pl` + `ip_iga_ron98_pl` (the ignition pair) | 640 | **yes** — with 96 B left for the directory and the two 16-byte injection curves (672 B total) |
| one `ip_map_ve_N` (512 B) | 512 | yes, but then the ignition pair does not fit (640 + 512 = 1152 > 736) |
| one ignition map + both `ip_af_target_*` | 320 + 384 = 704 | only with a very compact directory (704 + ~16 B ≈ 720) |
| all 8 VE maps | 4096 | **no** — not by a factor of five |
| both AFR target maps + the ignition pair | 1024 | **no** |

**So on this car the live overlay is an ignition feature, not a fuelling feature.** The VE maps
are the fuel map on MS43X001 and they cannot be shadowed here.

If live fuelling is wanted anyway, the options are:

1. **Per-cell deltas instead of a shadow.** The overlay stores `(cell index, delta)` pairs and
   the reader adds the delta to the flash value. A hundred changed cells in one VE map cost
   ~200 B instead of 512 B, so a working set of a few hundred cells fits. It needs a delta hook
   in the reader rather than an address substitution, so it costs more code and more time in the
   hot path, and the app has to compute and show the patched values.
2. **One VE map at a time** (512 B). The ECU blends two neighbouring overlap maps, so a single
   shadowed map leaves the blend half-live — the app would have to warn about it.
3. **Tune VE offline.** The app already edits the bin with the XDF; the owner flashes the
   result normally. No live path needed.

The natural first build is option "ignition pair live" — it fits with 64 bytes to spare, it
covers the owner's main interest, and it exercises the whole mechanism (stub, directory, DS2
command, key-on reset) before anything harder is attempted.

### Which tables, decided by looking at the tune

`TUNE_ANALYSIS.md` works out how the car's own calibration was made and which tables carry
the hand-made edits. The outcome:

- The tuner works on **`ip_iga_ron98_pl__n__maf`** (0x77315): +1.5° in the high-load columns
  from 3000 rpm up, plus the 6990 rpm row dropped to −23.6° for the "flames" band. RON91 was
  left at stock apart from that row.
- The fuelling knob is **`ip_af_target_ron98__maf__n`** (0x7D69C): the 6990 rpm column set to
  λ 0.781 for the flames band. There is no injection map on MS43X001 to tune.
- **Half the tune never reached the engine.** Every e85 table in the release is a byte-identical
  copy of its RON98 twin, and the blend helper 0D:1850 computes
  `base + (twin − base)·f/32` with the flex factor — which is 0 because `c_conf_ff` = 0 on this
  car. So the e85 tables are inert, and the tune's VANOS exhaust-cam edit (112 cells in
  `ip_cam_sp_e85_ex_pl`, with the live `ip_cam_sp_ron98_ex_pl` untouched) is a **no-op**.

**Live set (fits the 736 B with ~104 B spare):**

| Table | Address | Bytes |
|---|---|---|
| `ip_iga_ron98_pl__n__maf` | 0x77315 | 320 |
| `ip_af_target_ron98__maf__n` | 0x7D69C | 192 |
| `ip_iga_ron98_is__n__maf` | 0x775D4 | 36 |
| `ip_iga_puc__n__tco` | 0x7717D | 24 |
| `ip_ti_fac_map__map`, `ip_ti_fac_ti__ti` | 0x7D974, 0x7D984 | 32 |
| `c_inj_flow` | 0x70E14 | 2 |
| directory + flags | | ~26 |

RON91 (320 B) is left in flash — the octane blend works with one half in RAM. The MBT
reference (192 B) does not fit either. The VE maps are excluded on purpose: a VE map is the
load model, so editing it live moves everything at once, whereas a λ target is a bounded knob.

## 6. The K-line command surface

**Reading memory already works** — DS2 command 06, handler 0A:6A38, unchanged in the car
firmware [obs].

**Writing RAM does not exist as a general path.** The closest thing is the "adaptation write"
family: DS2 command **0x41**, sub-commands 4–9 (JMPI table at 0x0C:4608), each copying up to
64 payload bytes into a fixed RAM block (0x8221, 0x8321, 0x8421, 0x8521, 0x8621, 0x8721),
clamped to 0x80 [obs]. Those blocks are in use (0x8421–0x8460 is 62 of 64 bytes referenced) and
are learned adaptation values, so they cannot be repurposed. The write is also gated on
`c_write_ad_ena` (0x70DEF, value 0 on the car) and two status bits (FD78.6, FD2Ch.7).

**So a new command is needed.** The car's dispatcher (file 0x1FB76) still routes **0x6C and
0x6D** to 09:FFB6 — the "unknown" reply [obs]. In MS43X001 both are dead slots. Repointing
one of them costs 4 bytes:

```
01FC8A  da09b6ff   CALLS 09h, FFB6h     ->   da0cxxxx   CALLS 0Ch, xxxxh
```

The new handler lives in the free sector at CPU 0C:B545+ and would implement, for example:

| Sub | Function |
|---|---|
| 00 | status: overlay enabled, RAM class, free bytes, number of active entries |
| 01 | upload N bytes into the shadow area (address + data) |
| 02 | bind a shadow area to a table (flash address + size), activate |
| 03 | unbind / revert one table to stock |
| 04 | revert everything to stock |

The reply frame follows the existing helpers at 09:FF96 (length 4 + status byte: A0 ack,
A1 busy, A2 rejected, B0 parameter error, B1 function error, FF unknown) [obs].

## 7. Live in the car, with a passenger

The owner edits while the car is being driven, so the design has to be safe by construction:

- **Stock is the default and the fallback.** The overlay is off at every key-on; a crash,
  a reset or a lost K-line leaves the ECU on the flashed calibration.
- **Reverting is one command**, and reverting all tables is one command. The app should make
  "revert" a single, obvious, always-available action.
- **The flash stays authoritative.** Edits live in RAM until the owner saves them into a bin
  (with `tools/ms43_checksums.py --fix`) and flashes that normally. Nothing about the live path
  requires writing flash.
- **Latency.** The K-line runs at 9600 baud (the logger session at 125000 baud is a different
  mode). One ignition map is 320 B; at 9600 baud with the ~11-byte DS2 frame overhead that is
  roughly 0.4 s per upload, and the 8 VE maps (4096 B) about 5 s. Uploading only the table that
  changed keeps the passenger's edit visible within a second or two.
- **The ECU reads the shadow every cycle**, so an edit takes effect on the next load/ignition
  calculation without any reset or key cycle.

## 8. Open items

1. **Which tables the owner wants live.** With 8 KiB confirmed the choice is real and small:
   the ignition pair (640 B, fits) versus one VE map (512 B, fuelling, but then no ignition) or
   the AFR target maps. The candidate list is in §2; the budget is in §5.
2. **The stub's register budget** — the readers are stackless; the stub must be written so the
   emulator proves it does not disturb them.
3. **Program CRC coverage.** New code at CPU 0C:B545+ lies outside the program CRC range
   (which ends at 0C:A8CB) [obs]. The CRC descriptor must be extended, as MS43X did, and all
   five checksums recomputed (`tools/ms43_checksums.py --fix`). The program monitor sum covers
   only 0D:0000–0D:3BF8 and 0E:E876–0E:E878 and is unaffected by code placed at 0C:B545.
4. **The app side** lives in `MS43_LOGGER`; it already reads
   TunerPro XDFs, so the new MS43X001 XDF gives it named, scaled, car-accurate maps with no
   further definition work. It needs the live-edit command and the upload path added.
